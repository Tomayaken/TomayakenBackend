# 到着予測と物資配分

利用者の継続的な位置情報から、各避難所に「何人が、いつ頃到着しそうか」を予測し、その人数をもとに物資の不足・余剰と移送の提案を出す。

> 本書は検討中の設計である。各項目に **決定** / **案** / **未決** を付けている。案と未決が確定したら、[database.md](./database.md) / [api.md](./api.md) / [architecture.md](./architecture.md) / クライアントへの依頼事項に反映する。

## 1. 決定事項

| 項目 | 決定内容 |
| --- | --- |
| 予測の方式 | 位置の履歴から移動の向きと速さを求めて、行き先と到着時刻を推定する |
| 数え方 | 1台の位置情報を世帯の人数分として数える。同じ世帯で複数台が送っている場合は重複させない |
| 位置を送る条件 | activeな災害があり、本人が未チェックインの間だけ。アプリで明示的に同意した人だけが送る。チェックインしたら止める |
| 保持の方針 | 数分おきに取得した点を、直近の一定時間だけ保持し、それより古い点は捨てる |
| 物資の必要量 | `(現在人数 + 予測到着人数) × 1人あたりの必要量 × 想定日数` を在庫と比べる。毛布のように1人1つの物資は消費量として扱わない |
| 配分 | 避難所ごとの不足・余剰に加え、余剰のある避難所から不足する避難所への移送案を自動で作る。実行は既存の入庫・配布操作で手動 |
| 管理画面に見せる範囲 | 避難所ごとの予測人数（30分以内 / 60分以内 / 180分以内）のみ。個人の位置は見せない |

## 2. スマホから取れる位置情報

スマホの「GPS」の値は、GNSS（GPS等の衛星測位）・Wi-Fi・基地局・センサーをOSが組み合わせて推定した**位置の推定値**である。Flutter（`geolocator` の `Position`）、iOS（`CLLocation`）、Android（`Location`）でほぼ同じ値が取れる。

| 値 | 意味 | 注意点 |
| --- | --- | --- |
| `latitude` / `longitude` | 緯度・経度 | |
| `accuracy` | 水平精度（m） | 「この半径内に真の位置が約68%の確率で入る」という意味。屋外は5〜20m程度、屋内やビルの谷間では数十〜数百m |
| `timestamp` | 測位した時刻 | 送信時刻ではない |
| `speed` | 速さ（m/s） | OSが算出したその瞬間の値。屋外のGNSSではドップラー効果から求めるため精度が良いが、屋内やWi-Fi測位では無効値（-1や0）になりやすい |
| `heading` | 進行方向（真北から時計回りの角度） | 端末の向きではなく移動の向き。止まっていると無効値になる |
| `speedAccuracy` / `headingAccuracy` | 上記の精度 | 端末やOSのバージョンによっては取れない |
| `isMocked` | 偽装された位置か（Android） | 位置偽装アプリの検出に使える |

### 速さと向きを位置の差から求める理由

OSの `speed` / `heading` は「その瞬間」の値であり、数分おきに取得すると信号待ちなどの瞬間の値をたまたま拾うだけになる。屋内やバックグラウンドでは無効値も多い。

一方、位置の差から求める場合は、止まっていても位置がぶれる（`accuracy` が20mなら毎回20m程度動く）。判定に使う時間が短いと、このぶれが移動に見える。

- 20mのぶれ ÷ 2分 = 時速0.6km（ゆっくり歩く人と区別しにくい）
- 20mのぶれ ÷ 15分 = 時速0.08km（歩行と明確に区別できる）

このため、**15分程度の幅で、位置の差から**速さと向きを求めることを基本とし、OSの値は補助に使う。

## 3. 予測のアルゴリズム（案）

対象は、activeな災害中に位置を送っている未チェックインの利用者。1人ずつ「どの避難所へ、何分後に着きそうか」を求め、最後に避難所ごとに集計する。

```text
位置の点（直近60分を保持）
  ↓ ① 使えない点を除く
  ↓ ② 直近15分の点を取り出す
  ↓ ③ 移動の向きと速さを求める
  ↓ ④ 移動しているかを判定する（止まっていれば ④' 立ち止まり中の判定）
  ↓ ⑤ 行き先の避難所を決める
  ↓ ⑥ 到着予定を求める
  ↓ ⑦ 世帯人数を掛けて、避難所 × 時間幅ごとに合計する
避難所ごとの予測人数
```

### ① 使えない点を除く

| 条件 | 理由 |
| --- | --- |
| `accuracy` が100mを超える点 | 屋内やビルの谷間の点は数百mずれることがあり、向きの判定を狂わせる |
| `isMocked` が true の点 | 偽装された位置 |
| `recordedAt` が未来、または60分より前の点 | 端末時刻の異常や、保持期間を過ぎた点 |

### ② 直近15分の点を取り出す

最新の点から15分さかのぼった範囲を使う。**3点以上、かつ最初の点から最後の点まで5分以上**ない場合は、③〜⑤の判定をせず「データが足りないとき」の扱いにする。短い時間ではぶれと移動を区別できないため。

### ③ 移動の向きと速さを求める

- ぶれを抑えるため、**最初の3点の平均位置**を始点、**最後の3点の平均位置**を終点とする。
- 始点〜終点の直線距離（haversine式）を `d`、経過時間を `t` として、速さ = `d / t`、向き = 始点から終点への方位（0〜360°）。

### ④ 移動しているかを判定する

`d > max(150m, 点の accuracy の中央値 × 3)` なら移動しているとみなす。

- 150mは「15分の平均で時速0.5km」（0.5km/h × 15分 ≈ 125m）に余裕を持たせた値。速さと距離は同じ基準の言い換えで、判定には距離を使う。
- 屋外で止まっている人のぶれは5〜20m程度で、始点・終点は3点平均なので、見かけの移動は数十mに収まる。150mはぶれだけでは超えない。
- `accuracy × 3` は、精度が悪い環境でしきい値を自動的に厳しくするための項。
- ゆっくり歩く人でも150mを大きく超える。

| 歩く人 | 速さ | 15分で進む距離 |
| --- | --- | --- |
| 通常の歩行 | 時速4km | 約1,000m |
| 高齢者・子ども連れ | 時速2km | 約500m |
| がれきの中など | 時速1km | 約250m |

移動していない人は、④' の判定をしたうえで、該当しなければ予測に含めない（自宅等で待機している人を数えないため）。

### ④' 立ち止まり中の判定（案）

直近15分の判定だけでは、避難の途中で休憩したりコンビニに寄ったりした人が予測から一時的に消え、歩き出すと戻ってくる。管理画面の数字が増減して分かりにくい。

| 立ち止まった長さ | 直近15分だけで判定した場合 |
| --- | --- |
| 1〜2分（信号待ち） | 移動中。平均の速さが少し下がる |
| 5〜10分（休憩） | 移動中。平均の速さが時速2km前後に下がり、到着予定が遅めに出る |
| 13分以上 | **移動していないと判定され、予測から消える** |
| 店などに入る | 精度の悪い点が除かれ、点が足りずに**予測から消える** |

そこで、直近15分で「移動していない」か「データ不足」になった人は、**15〜45分前の点**で③〜⑤の判定をやり直す。

| 直近15分 | 15〜45分前 | 扱い |
| --- | --- | --- |
| 移動している | （見ない） | 移動中 |
| 止まっている / データ不足 | 避難所へ向かって移動していた | **立ち止まり中** として数え続ける |
| 止まっている | 止まっていた | 落ち着いた（避難所以外に滞在）とみなし、数えない |
| データ不足 | 点がない | 判定待ちとして数えない |

- 立ち止まり中の行き先は、移動していた時点で決まった避難所。到着予定は、**現在地から**の距離 × 1.3 ÷ 時速4km（再び歩き出す前提）。
- **直近30分ずっと止まっている**人は予測から外す。
- 前回の判定結果を保存する必要はなく、毎回60分の履歴から計算できる。60分の履歴を保持する理由の一つでもある。

### ⑤ 行き先の避難所を決める

1. **避難所から100m以内にいる人**は、その避難所に「到着済み・未チェックイン」として数える（到着予定0分）。
2. 各避難所について、移動の向きと避難所への方位の差（0〜180°）を求める。
3. 差が **±45°以内** の避難所を候補とし、その中で最も近い避難所を行き先とする。
   - ±45°の幅は、人が道に沿って曲がりながら進むことへの余裕。
4. 候補がない場合の扱いは未決（[論点A](#論点a-移動しているが45以内に避難所がない人)）。

### ⑥ 到着予定を求める

到着予定 = `直線距離 × 1.3 ÷ 速さ`

- 1.3は、道に沿って歩くと直線距離より長くなることの補正。市街地の道のりは直線距離の1.2〜1.4倍程度になることが多い。
- 速さは時速2〜6kmに収める。車での移動や、ぶれによる極端な値で予測がおかしくならないようにするため。
- 休憩を挟むと平均の速さが下がり到着予定が遅めに出るが、下限が時速2kmなので遅れは最大2倍程度。物資の計算には180分以内の人数を使うため、影響は小さい。

### ⑦ 集計

- 1人あたりの数に**世帯人数**を掛ける。同じ世帯で複数人が位置を送っている場合は、最新の点を持つ1人だけを使う。
- 時間幅は累積（30分以内の人は60分・180分以内にも含む）。180分を超える人は数えない。
- 管理画面には避難所ごとの合計だけを返す。判定方法（下記 `method`）別の内訳を付ける。

```ts
// 1人ごとの推定結果（内部用。APIでは返さない）
type ArrivalEstimate = {
  userId: string;
  householdSize: number;
  shelterId: string;
  etaMinutes: number;
  method: "nearby" | "declared" | "heading" | "os_heading" | "paused";
};
```

### データが足りないとき

②の条件を満たさなくても、最新の点のOSの `speed` が0.5m/s以上で `heading` が有効なら、それを③の代わりに使う（`os_heading`）。それもなければ④' の判定を行い、該当しなければ判定待ちとして数えない。

### 計算例

山田さん（世帯3人）の直近15分で、始点〜終点が950m、向き40°、点の精度は約15m。

- 判定のしきい値は `max(150, 15 × 3) = 150m`。950m > 150m なので移動している。
- 速さは 0.95km ÷ 0.25時間 = 時速3.8km。

| 避難所 | 方位 | 向きとの差 | 距離 | 判定 |
| --- | --- | --- | --- | --- |
| 第一小学校 | 55° | 15° | 1.2km | 候補 |
| 中央公民館 | 100° | 60° | 0.8km | 範囲外 |
| 市民体育館 | 220° | 180° | 0.5km | 範囲外（後方） |

- 行き先は第一小学校。最寄りで決めると中央公民館になるが、向きを使うことで区別できる。
- 到着予定 = 1.2km × 1.3 ÷ 時速3.8km ≈ 25分。第一小学校の30分以内・60分以内・180分以内に各 +3人。

## 4. パラメータ一覧（案）

すべて設定値とし、デモ前に実際に歩いて調整できるようにする。

| 項目 | 値 | 理由 |
| --- | --- | --- |
| 判定に使う時間 | 15分 | 2分程度ではぶれが移動に見える。15分ならぶれ（数十m）より歩行距離（約1km）が十分大きい |
| 最低限の点数・時間幅 | 3点・5分 | 始点・終点を3点平均にするため。5分未満ではぶれと移動を区別できない |
| 精度の上限 | 100m | 屋内等の大きくずれた点を除く |
| 移動とみなす距離 | 150m（または精度の中央値 × 3 の大きい方） | 15分で時速0.5km相当。ぶれでは超えず、時速1kmの歩行でも超える |
| 方位の許容範囲 | ±45° | 道に沿って曲がりながら進むことへの余裕 |
| 迂回係数 | 1.3 | 市街地の道のりは直線距離の1.2〜1.4倍程度 |
| 速さの範囲 | 時速2〜6km | 車の移動やぶれによる極端な値を抑える |
| 到着済みとみなす半径 | 100m | 避難所の敷地付近で未チェックインの人を拾う |
| 立ち止まり中の再判定 | 15〜45分前の点 | 直近15分の前の移動を確認する |
| 予測から外すまでの停止時間 | 30分 | 休憩・立ち寄りは数え続け、長時間止まった人は避難所以外に落ち着いたとみなす |
| 立ち止まり中の想定速度 | 時速4km | 再び通常の速さで歩き出す前提 |
| 位置の保持期間 | 60分 | 立ち止まり中の判定に15〜45分前の点が必要 |
| 取得間隔 | 2分 | 60分で最大30点程度に収まる |

## 5. 既知の限界

- 川・線路などで道が大きく迂回する場合、向きの判定が外れることがある。
- 車で移動している人の到着予定は遅めに出る（速さの上限を時速6kmにしているため）。
- バックグラウンドではOSの都合で取得間隔がずれることがある。サーバー側はそれを前提にする。
- 位置情報は自己申告であり、偽装を完全には防げない（`isMocked` はAndroidのみ）。

## 6. 未決事項

### 論点A: 移動しているが±45°以内に避難所がない人

- (a) 数えない（親戚の家などに向かっている可能性がある）
- (b) 最寄りの避難所に数える（多めに見積もる）

案は (b)。物資の不足を見落とすほうが危ないため、予測は多めに出す。

### そのほか

| 論点 | 案 |
| --- | --- |
| 行き先の申告 | アプリで申告されたら推定より優先する（`declared`）。申告機能はアプリ側の優先度を低くする |
| バックグラウンド取得 | 依頼事項には書くが、最低限アプリを開いている間の送信を必須とする |
| 古い点の削除 | 位置を受け取ったときに、そのユーザーの60分より古い点を消す（Lambdaに定期実行を足さない）。災害終了時に全削除 |
| 位置を送るAPI | `POST /api/v1/me/locations` で複数件をまとめて受け取る（通信が途切れたときの再送のため）。チェックイン済みやactive災害なしの場合は点を捨てて `{ "tracking": false }` を返し、アプリは送信を止める |
| 予測を取得するAPI | `GET /api/v1/admin/forecast/arrivals` と `GET /api/v1/admin/forecast/supplies?days=1`。リクエストのたびに計算し、管理画面は30秒おきにポーリング |
| 物資の必要量に使う人数 | 現在人数 + 180分以内の予測到着人数 |
| 物資マスタの追加項目 | 1人1日あたりの必要量、`consumption_type`（`daily` / `per_person`） |
| 移送案の作り方 | 不足する避難所に、近い余剰避難所から順に割り当てる |
| 実装優先順位 | Supply の直後に入れ、最小デモに「到着予測と配分案を見る」を追加する |
